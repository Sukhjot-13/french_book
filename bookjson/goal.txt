# L’Étude Master JSON Construction Pipeline

## Complete Implementation Specification

## 1. Objective

We already have separate JSON files for different textbook chapters.

These JSON files are **not raw extraction output**. They already follow a reasonably structured schema, but:

- some chapters may contain fields that other chapters do not;
- the same concept may occasionally use different field names;
- some objects may contain additional nested information;
- some fields may be missing;
- some data may be incomplete;
- the same verb, vocabulary item, construction, tense, grammar rule, expression, etc. may appear in multiple chapters;
- some information must eventually be enriched using AI.

The goal is to construct a **single canonical master dataset** without losing any information from any chapter.

The process must be deterministic and auditable.

AI must NOT simply read all chapter files and generate a new master JSON from memory.

Instead, build scripts that:

1. inspect all existing chapter JSONs;
2. compare their schemas;
3. identify every field variation;
4. compare them against the proposed master schema;
5. report unmapped or conflicting fields;
6. normalize chapter data;
7. merge duplicate entities;
8. detect conflicts;
9. verify that nothing was lost;
10. identify missing information;
11. prepare controlled AI enrichment batches;
12. validate enrichment results;
13. generate the final master JSON;
14. allow new data to be added later using the same pipeline.

---

# 2. Fundamental Architecture Rules

## Rule 1 — Never silently discard data

If a source chapter contains a field that the canonical schema does not understand, do NOT ignore it.

It must appear in an audit report such as:

```json
{
  "entity_type": "verb",
  "field": "special_usage",
  "files": ["chapter_07.json", "chapter_11.json"],
  "status": "unmapped"
}
```

The developer must decide whether:

- it maps to an existing canonical field;
- it deserves a new canonical field;
- it belongs to another entity type;
- it is redundant;
- it is parsing noise.

Until explicitly resolved, it must remain reported.

---

## Rule 2 — Do not use artificial IDs in the canonical JSON

The human-readable data should use natural references.

Example:

```json
{
  "base_verb": "prendre"
}
```

instead of:

```json
{
  "verb_id": "verb_00483"
}
```

Another example:

```json
{
  "related_tense": "conditionnel présent"
}
```

Natural references should normally use:

```text
entity category + canonical name
```

The entity category provides the namespace.

For example:

```text
verbs → prendre
tenses → conditionnel présent
constructions → demander à quelqu'un de + infinitif
```

The final JSON does not need UUIDs.

A database may later use internal IDs when importing this data.

---

# 3. Natural Key Rules

Different entity types require different canonical keys.

## Verbs

Canonical infinitive.

Examples:

```text
prendre
venir
lever
se lever
se souvenir
s'attendre
```

`lever` and `se lever` are separate verbs.

`attendre` and `s'attendre` are separate verbs.

---

## Tenses

Canonical French tense name.

Examples:

```text
présent
passé composé
imparfait
plus-que-parfait
futur simple
futur antérieur
conditionnel présent
conditionnel passé
```

---

## Constructions

Canonical normalized construction.

Example:

```text
demander à quelqu'un de + infinitif
```

---

## Collocations

Canonical phrase.

Example:

```text
prendre une décision
prendre sa retraite
avoir besoin de
```

---

## Expressions

Canonical expression text.

---

## Grammar rules

Use a canonical descriptive rule name.

Example:

```text
si + imparfait → conditionnel présent
```

Do not rely on vague names such as:

```text
rule 1
grammar point
special case
```

---

## Vocabulary

Vocabulary requires more caution.

The same French spelling can potentially represent different parts of speech or meanings.

Internally, deduplication may therefore use:

```text
normalized_french + part_of_speech
```

Example:

```text
orange|noun
orange|adjective
```

The final JSON does not necessarily have to expose this combined string.

# PHASE 1 — SOURCE FILE DISCOVERY

# 5. Script 01 — `01_inventory_files.py`

## Purpose

Discover every chapter JSON and verify that files are readable.

## Checks

For every file:

- filename;
- JSON validity;
- top-level type;
- chapter number;
- chapter title;
- file size;
- top-level fields;
- whether required chapter metadata exists.

## Output

```text
audit/file_inventory.json
```

Example:

```json
{
  "total_files": 19,
  "valid_json": 19,
  "invalid_json": 0,
  "chapters": [
    {
      "file": "chapter_12.json",
      "chapter_number": 12,
      "chapter_title": "Could, Should, Would?",
      "top_level_fields": [
        "grammar_rules",
        "verbs",
        "vocabulary",
        "expressions"
      ]
    }
  ]
}
```

## Critical checks

Detect:

- duplicate chapter numbers;
- missing chapter numbers;
- malformed JSON;
- empty files;
- unexpected non-JSON files.

The script must fail validation if a required source file cannot be parsed.

# PHASE 2 — SCHEMA DISCOVERY

# 6. Script 02 — `02_extract_schema_paths.py`

## Purpose

Since the files are already semi-structured, discover **every field path actually used anywhere**.

Recursively inspect every JSON object.

Example source:

```json
{
  "verbs": [
    {
      "infinitive": "prendre",
      "conjugations": {
        "present": {
          "je": "prends"
        }
      }
    }
  ]
}
```

Must produce paths such as:

```text
verbs[]
verbs[].infinitive
verbs[].conjugations
verbs[].conjugations.present
verbs[].conjugations.present.je
```

Do this for every entity.

## Record

For every path:

- number of files containing it;
- number of occurrences;
- files containing it;
- detected value types;
- sample values.

Example:

```json
{
  "path": "verbs[].past_participle",
  "files_count": 11,
  "occurrences": 43,
  "types": ["string"],
  "sample_values": ["pris", "fait", "venu"]
}
```

## Output

```text
audit/schema_inventory.json
```

---

# 7. Script 03 — `03_detect_schema_variations.py`

## Purpose

Determine where chapter schemas differ.

Because the files already share a rough schema, this script should answer:

> Which fields are standard, which are optional, and which occur only in a few chapters?

Classify fields as:

```text
universal
common
occasional
rare
unique
```

Suggested thresholds:

```text
universal = 100% files where entity occurs
common = >= 70%
occasional = 30–69%
rare = 2–29%
unique = one source file
```

These percentages are diagnostic only.

Never assume a rare field is unimportant.

## Output

```text
audit/schema_variations.json
audit/field_frequency.json
```

# 9. Script 04 — `04_compare_source_to_master_schema.py`

Compare every discovered source path against the proposed master schema.

Classify source fields into:

```text
EXACT_MATCH
KNOWN_ALIAS
POSSIBLE_ALIAS
UNMAPPED
TYPE_CONFLICT
STRUCTURE_CONFLICT
```

Example:

```text
verbs[].english
verbs[].meaning
verbs[].translation
```

may all potentially map to:

```text
verbs[].meanings
```

But the script must NOT make semantic guesses automatically unless the mapping is already defined.

Unknown possibilities should be reported.

## Output

```text
audit/mapping_candidates.json
audit/unknown_fields.json
```

# PHASE 4 — FIELD-MAPPING REVIEW

# 10. Create `field_mappings.json`

All known schema variations must be configured outside transformation code.

Example:

```json
{
  "verb": {
    "infinitive": ["infinitive", "verb", "base_form"],
    "meanings": [
      "meaning",
      "meanings",
      "english",
      "translation",
      "translations"
    ],
    "past_participle": ["past_participle", "participe_passe"]
  }
}
```

Mappings must support nested paths when necessary.

---

# 11. Important: Mapping is NOT always renaming

Determine whether a source field requires:

### Direct rename

```text
english → meanings
```

### Scalar-to-array conversion

```json
"meaning": "to take"
```

becomes:

```json
"meanings": ["to take"]
```

### Object restructuring

Example:

```json
"future_stem": "prendr-"
```

might become:

```json
"stems": {
  "futur simple": "prendr-"
}
```

### Entity extraction

Example:

```json
{
  "verb": "prendre",
  "expressions": ["prendre une décision"]
}
```

The expression may need to become its own top-level entity.

The verb should then reference it naturally.

### Semantic split

One source field may contain multiple concepts and need separation.

### Semantic merge

Multiple source fields may represent one canonical concept.

---

# 12. Script 05 — `05_validate_field_mappings.py`

Before normalization starts, verify:

- every source field is accounted for;
- every mapping points to a valid canonical field;
- no incompatible fields are accidentally mapped together;
- data types are compatible;
- no field is silently ignored.

Output:

```text
audit/unresolved_mappings.json
```

Normalization must NOT be considered final while unresolved mappings remain.

# PHASE 5 — NORMALIZATION RULES

# 13. Create `normalization_rules.json`

Normalization must be conservative.

Do not modify meaningful French text unnecessarily.

Rules may cover:

### Whitespace

```text
" prendre " → "prendre"
```

### Unicode apostrophes

Normalize equivalent apostrophe characters when appropriate.

Example:

```text
s’attendre
s'attendre
```

Choose one canonical representation.

### Case

Natural keys may be lowercase:

```text
Prendre → prendre
```

while preserving original display text if useful.

### Tense aliases

```text
conditionnel present
conditionnel présent
conditional present
```

→

```text
conditionnel présent
```

### Part-of-speech aliases

```text
noun
nom
n.
```

→ canonical value.

### Gender aliases

```text
masc
masculine
m
```

→

```text
masculine
```

### Verb group aliases

Normalize consistent representation.

---

# 14. Never perform dangerous normalization

Do NOT blindly:

- remove accents;
- remove `se`;
- alphabetically rearrange phrases;
- remove prepositions;
- stem French words;
- singularize everything;
- collapse expressions that merely look similar.

For example:

```text
attendre
s'attendre
```

must never merge.

Likewise:

```text
parler à quelqu'un
parler de quelque chose
```

are not the same construction.

---

# PHASE 6 — NORMALIZE EACH CHAPTER

# 15. Script 06 — `06_normalize_chapters.py`

Transform every chapter file independently into the canonical schema.

Do NOT merge chapters yet.

Output:

```text
normalized/chapter_01.normalized.json
...
```

This intermediate stage is essential.

It lets us compare:

```text
source chapter
vs
normalized chapter
```

before deduplication complicates things.

---

# 16. Normalization must preserve provenance

Every canonical entity should at minimum know which chapter(s) supplied it.

Example:

```json
{
  "infinitive": "prendre",
  "source_chapters": [8]
}
```

When later merged:

```json
{
  "source_chapters": [3, 8, 12]
}
```

Fine-grained source file/path information can remain in audit files rather than bloating the final JSON.

---

# 17. Script 07 — `07_validate_normalized_chapters.py`

For each normalized chapter verify:

- valid JSON;
- canonical schema compliance;
- no unmapped fields;
- all source entities accounted for;
- natural keys present;
- expected arrays are arrays;
- expected objects are objects;
- no data disappeared because of null-handling;
- no duplicate values were accidentally introduced.

Create:

```text
audit/normalization_report.json
```

# PHASE 7 — LOSSLESSNESS / COVERAGE VALIDATION

# 18. Script 08 — `08_source_normalization_coverage.py`

This is one of the most important scripts.

It must compare the original chapter JSONs against normalized chapter JSONs.

For every source value determine one of:

```text
PRESERVED
NORMALIZED
MOVED
MERGED
INTENTIONALLY_EXCLUDED
UNACCOUNTED_FOR
```

There should be **zero `UNACCOUNTED_FOR` source values** before proceeding.

Do not rely only on object counts because restructuring can alter counts.

Track mapping at field/value level during transformation.

Output:

```text
audit/coverage_report.json
```

Summary example:

```json
{
  "source_fields_seen": 18452,
  "preserved": 16210,
  "normalized": 1940,
  "moved": 302,
  "unaccounted_for": 0
}
```

# PHASE 9 — DUPLICATE DETECTION

# 21. Script 10 — `10_detect_duplicates.py`

Before merging, identify duplicates using natural keys.

Create categories:

```text
EXACT_DUPLICATE
NORMALIZED_DUPLICATE
POSSIBLE_DUPLICATE
DISTINCT
```

Examples:

```text
"Prendre"
"prendre "
```

→ normalized duplicate.

But:

```text
prendre
se prendre
```

→ distinct.

---

# 22. Fuzzy matching must never auto-merge

Fuzzy similarity can generate suggestions:

```text
demander à qn de faire
demander à quelqu'un de + infinitif
```

But fuzzy matches must go into:

```text
audit/possible_duplicates.json
```

unless explicitly approved through deterministic rules.

Never let edit distance automatically merge French linguistic structures.

# 24. Verb merge examples

## `source_chapters`

Use:

```text
UNION_UNIQUE
```

---

## `meanings`

Usually:

```text
UNION_UNIQUE
```

---

## `past_participle`

Use:

```text
CONFLICT_IF_DIFFERENT
```

If chapter A says:

```text
pris
```

and chapter B says:

```text
prendre
```

do not choose automatically.

Report conflict.

---

## `auxiliary`

Usually:

```text
CONFLICT_IF_DIFFERENT
```

unless schema intentionally permits multiple auxiliaries.

---

## `conjugations`

Use:

```text
DEEP_MERGE
```

Example:

Chapter 7 contains:

```text
passé composé
```

Chapter 11 contains:

```text
conditionnel présent
```

Both must survive.

---

## `examples_by_tense`

Use:

```text
UNION_UNIQUE
```

possibly preserving textbook order.

---

## `constructions`

Use:

```text
UNION_UNIQUE
```

# PHASE 11 — BUILD SOURCE MASTER

# 25. Script 11 — `11_build_master_source.py`

Merge all normalized chapter data.

Output:

```text
master/master.source.json
```

This file should represent:

> Everything derivable from the source chapter JSONs after deterministic normalization and merging, but before external AI enrichment.

This file is extremely important.

It gives us a clean textbook-derived baseline.

---

# 26. Suggested master structure

Prefer natural-key dictionaries for strongly deduplicated entities.

Example:

```json
{
  "verbs": {
    "prendre": {
      "infinitive": "prendre"
    },

    "venir": {
      "infinitive": "venir"
    },

    "se souvenir": {
      "infinitive": "se souvenir"
    }
  }
}
```

This gives simple access:

```javascript
master.verbs["prendre"];
```

---

# 27. Chapters should remain accessible

Even though the dataset is global-first, preserve chapter organization.

For example:

```json
{
  "chapters": {
    "12": {
      "chapter_number": 12,
      "title": "Could, Should, Would?",
      "verbs": [
        "pouvoir",
        "devoir",
        "vouloir"
      ],
      "tenses": [
        "conditionnel présent",
        "conditionnel passé"
      ],
      "grammar_rules": [...]
    }
  }
}
```

Thus the same data supports:

```text
global revision
```

and:

```text
chapter revision
```

without duplicating full entity objects unnecessarily.

# PHASE 19 — AI RETURNS PATCHES, NOT FULL ENTITIES

# 39. Required enrichment response format

AI should return patches such as:

```json
{
  "entity_type": "verb",
  "key": "prendre",
  "patch": {
    "past_participle": "pris",
    "auxiliary": "avoir",
    "future_stem": "prendr-"
  }
}
```

Do NOT ask the AI to reproduce the complete `prendre` object.

This prevents accidental deletion of:

```text

constructions

other metadata
```

# PHASE 20 — VALIDATE AI RESPONSES

- strings not empty;

- no duplicate values;
- no unrelated fields added.

# PHASE 25 — REGRESSION TESTS

# 48. Create automated tests

At minimum test:

### Verb distinction

```text
lever != se lever
attendre != s'attendre
```

### Merge

Multiple appearances of:

```text
prendre
```

create one global verb.

### Chapter provenance

If `prendre` occurs in chapters:

```text
3, 8, 12
```

result must contain:

```json
"source_chapters": [3, 8, 12]
```

### Deep conjugation merge

One chapter containing imparfait and another containing conditionnel must preserve both.

### Conflict detection

Different past participles must create a conflict rather than overwrite.

### Unknown field

A newly added source field must cause the schema audit to flag it.

### Broken reference

A construction referring to nonexistent verb must fail reference validation.

### Losslessness

Removing a mapping must cause coverage checks to fail.

# 51. Special requirement — no unnecessary duplication

Do not copy full verb objects into constructions, chapters, expressions, etc.


# 52. Special requirement — examples

Examples may appear:

For many use cases, keeping examples nested under relevant entities may be simpler.

Do NOT prematurely force every example into a global reference system.

First inspect the source data and actual application requirements.

The scripts should be generic.


# 56. Do not automatically fix semantic uncertainty

The pipeline may automatically fix structural certainty.

Safe examples:

```text
trim whitespace
normalize known tense alias
convert meaning string to meanings array
merge identical chapter numbers
```

Unsafe examples:

```text
deciding two constructions mean the same thing
correcting a French meaning
deciding an unusual field is useless
merging similar grammar rules
changing a textbook example
```

Unsafe cases must enter a review report or a targeted AI-resolution process.

# 59. Important Instructions to the Coding AI

Do not assume the proposed master schema is automatically correct.

The existing chapter JSONs are the evidence.

Before normalizing anything:

1. inspect all source schemas;
2. identify all fields;
3. identify field-name variations;
4. identify structural variations;
5. report anything not represented by the proposed master schema.

Do not remove information simply to make source data fit the schema.

When source information exposes an important concept missing from the master schema, propose a schema change.

# 61. Non-Negotiable Invariants

The completed system must satisfy all of these:

```text
1. No source information silently disappears.

2. Unknown fields are reported.

3. Duplicate entities are merged only using safe deterministic rules.

4. Fuzzy matches are suggestions, never silent merges.

5. Conflicting facts are reported rather than overwritten.

6. Every natural reference resolves.

7. Reflexive and non-reflexive verbs remain distinct.

8. Chapter provenance survives global merging.

9. Textbook-derived data can be separated from AI enrichment.

10. AI enrichment uses patches, not complete object rewrites.

11. AI responses are validated before insertion.

12. The master file can be rebuilt deterministically.

13. New data can later enter through the same ingestion pipeline.

14. The JSON does not depend on artificial internal IDs.

15. Database IDs, if eventually used, remain a database implementation detail.

16. `master.source.json` must account for 100% of intentionally preserved source information.

17. The final master should support both chapter-based revision and global collective revision.
```
