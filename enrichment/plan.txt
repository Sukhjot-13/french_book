L’ÉTUDE — FULL MANUAL AI ENRICHMENT PIPELINE
DETAILED IMPLEMENTATION SPECIFICATION
ALL MASTER COLLECTIONS

==================================================
1. PURPOSE
==================================================

Build a safe, deterministic, auditable enrichment system for the complete
`MASTER_DATA.json`.

The AI side will be MANUAL and high-quality:

1. A local script generates a batch.
2. The batch contains:
   - complete instructions;
   - selected entities;
   - relevant existing context;
   - allowed fields;
   - exact JSON response schema.
3. The batch is manually pasted into a high-quality GPT chat.
4. GPT returns PATCH JSON only.
5. The response is saved locally.
6. A validator checks the response.
7. A preview script shows the exact proposed changes.
8. The user reviews the diff.
9. Only an approved patch is applied.
10. The complete master dataset is validated again.
11. A deterministic audit log is written.

AI must NEVER directly rewrite `MASTER_DATA.json`.

AI must NEVER return a complete replacement master database.

AI must NEVER be trusted to perform the final merge.

The deterministic scripts remain authoritative.

==================================================
2. MASTER COLLECTIONS COVERED
==================================================

The pipeline must support ALL meaningful enrichable collections in the master:

- chapters
- topics
- concepts
- grammar_rules
- tenses
- verbs
- expressions
- vocabulary
- examples
- exercises
- exceptions_and_traps

Also recognize:

- unresolved_items
- source_quality

However:

`unresolved_items` and `source_quality` should NOT be automatically enriched
by default because they are audit/source-integrity collections.

They may be included later through a separate explicit review workflow.

The system must be designed so that new collections can be added easily.

==================================================
3. CORE SAFETY PRINCIPLES
==================================================

A. EXISTING MASTER DATA IS AUTHORITATIVE

Existing data came from the deterministic migration and source material.

AI enrichment must not silently:

- delete existing values;
- replace existing source-derived values;
- rewrite entire entities;
- remove provenance;
- remove chapter links;
- remove cross-references;
- remove examples;
- change exercise answers;
- alter source quotations;
- alter existing textbook examples;
- alter existing conjugations unless explicitly allowed;
- reinterpret existing source classifications.

B. PATCHES ONLY

GPT returns only explicit additions or proposed field operations.

Never return full entities unless the batch instructions specifically require
a complete new nested object that does not already exist.

C. NATURAL REFERENCES

No artificial enrichment IDs.

Use master natural keys.

Examples:

Verb:
"prendre"

Expression:
"prendre une décision"

Tense:
"conditionnel présent"

Grammar rule:
canonical rule name

Concept:
canonical concept name

Vocabulary:
{
  "canonical_form": "tour",
  "part_of_speech": "noun"
}

Example:
normalized French sentence or another existing natural example key used by the
master.

Exercise:
chapter_number + exercise_code

Trap:
normalized title + category

Chapter:
chapter_number

D. DETERMINISTIC MERGING

All changes must use predefined operations.

E. NO SILENT DATA LOSS

If something cannot be applied safely, reject it or mark it as a conflict.

F. VALIDATE EVERYTHING

Validation occurs:

- before preview;
- before apply;
- after apply;
- against MASTER_SCHEMA;
- against natural-reference rules;
- against duplicate rules.

11. SAFE PATCH OPERATIONS
==================================================

The validator/apply script should understand a SMALL, explicit operation set.

Recommended operations:

1. add_unique

Use for arrays of scalar values or natural references.

Example:

{
  "operation": "add_unique",
  "field": "synonyms",
  "values": ["saisir"]
}

Behavior:

- preserve existing values;
- append only unique new values;
- normalize for duplicate comparison;
- never delete.

2. set_if_empty

Use for singleton fields.

Example:

{
  "operation": "set_if_empty",
  "field": "register",
  "value": "neutral"
}

Behavior:

- if null/empty -> set;
- if same value -> no-op;
- if different non-empty value -> conflict;
- never overwrite automatically.

3. add_object_unique

Use for nested list objects such as:

- senses;
- usage entries;
- transformations;
- pattern slots;
- source-independent enrichment objects.

Must use deterministic natural uniqueness rules.

4. fill_nested_if_empty

Use to fill a missing nested field.

Example:

{
  "operation": "fill_nested_if_empty",
  "field": "formation.stem_rule",
  "value": "..."
}

5. add_conjugation_if_missing

For a complete missing verb+tense conjugation object.

Must NOT overwrite existing conjugation forms.

6. fill_conjugation_form_if_empty

For one missing person form.

If a form exists and differs:
CONFLICT.

7. add_example_link

Use to connect existing examples to entities.

Do not duplicate examples.

8. add_new_example

Use only when AI-generated example generation is explicitly enabled.

The example must be a NEW global example object and must later be deduplicated
against existing examples.

9. add_relation

For cross-links:

- verb -> expression;
- expression -> verb;
- rule -> tense;
- example -> verb;
- trap -> rule;
- etc.

Reference must resolve to an existing natural entity OR be added in the same
approved patch in a dependency-safe way.

10. propose_replace

DO NOT AUTO-APPLY.

This is a review-only operation.

Use only when GPT believes an existing value may be incorrect.

Example:

{
  "operation": "propose_replace",
  "field": "auxiliary",
  "existing": "avoir",
  "proposed": "both",
  "reason": "..."
}

The apply script must skip this unless manually converted into an approved
replacement operation.

11. replace_existing

Disabled by default.

Only an explicitly approved patch file created after human review may contain
this operation.

22. SCRIPT 4 — apply_enrichment.py
==================================================

PURPOSE

Safely apply an APPROVED patch to master.

Only approved patch files should be accepted by default.

Steps:

1. load MASTER_DATA.json;
2. calculate SHA-256 hash;
3. create backup;
4. load approved patch;
5. revalidate patch;
6. apply operations IN MEMORY;
7. deduplicate lists;
8. normalize natural references;
9. validate complete result against MASTER_SCHEMA;
10. run natural-reference validation;
11. run duplicate checks;
12. run structural integrity checks;
13. if ANY critical validation fails:
    - do not overwrite master;
    - write failure report;
14. if all pass:
    - write updated master atomically;
15. calculate new SHA-256;
16. write audit log.

==================================================

show warning before applying.

==================================================
31. STALE BATCH PROTECTION
==================================================

Because manual batches may sit for some time:

store the master hash when the batch is generated.

Before apply:

compare current master hash with batch base hash.

If different:

do NOT necessarily reject automatically.

Instead:

- re-evaluate every operation against current master;
- detect values already filled;
- convert duplicates to no-op;
- surface new conflicts;
- require preview again.

==================================================
32. DEPENDENCY HANDLING
==================================================

An AI patch may reference another entity.

Example:

verb "prendre"
synonym -> "saisir"

Before apply:

- confirm "saisir" exists as a verb;
- otherwise reject that relation OR mark unresolved.

Never create a new entity silently just because a reference is missing.

If AI proposes a genuinely new entity, use a separate:

add_new_entity

operation requiring explicit approval.

==================================================
33. NEW ENTITY CREATION
==================================================

Disabled by default.

If enabled:

AI must provide a complete minimum-valid object for that collection.

The script must:

- validate against schema;
- confirm natural key does not exist;
- check for near duplicates;
- require explicit review;
- add only after approval.

This is especially relevant later for:

- new expressions;
- new examples;
- new traps;
- new concepts.

==================================================
34. DUPLICATE HANDLING
==================================================

Arrays:

Use normalized unique union.

Examples:

"Very common."
and
"very common"

may be normalization-equivalent depending on field-specific rules.

French text should preserve accents and punctuation in stored values while
using normalized forms for duplicate detection.

Do NOT fuzzy-merge semantically different content automatically.

==================================================
35. CONFLICT HANDLING
==================================================

A conflict occurs when:

- master has a non-empty singleton;
- AI proposes a different value.

Example:

existing:
"register": "formal"

proposed:
"register": "neutral"

Result:

CONFLICT

Do not overwrite.

Store:

{
  "entity_type": "verb",
  "entity_key": "...",
  "field": "register",
  "existing": "formal",
  "proposed": "neutral",
  "reason": "existing singleton differs"
}

==================================================
36. HIGH-RISK VS LOW-RISK ENRICHMENT
==================================================

LOWER RISK

- aliases;
- search terms;
- synonyms;
- antonyms;
- register;
- additional English meanings;
- concise usage notes;
- relation links;
- tags.

MEDIUM RISK

- extra senses;
- example translations;
- concept explanations;
- grammar summaries;
- trap explanations;
- exercise hints.

HIGHER RISK

- conjugations;
- irregular stems;
- auxiliary;
- verb group;
- preposition requirements;
- agreement rules;
- grammar exceptions;
- correct/incorrect trap claims;
- exercise answers;
- tense formation rules.

Higher-risk batches should:

- be smaller;
- include more source context;
- be manually reviewed more carefully;
- never overwrite existing values automatically.

==================================================

The generated prompt should make the desired output explicit:

"Your entire response must be valid JSON and nothing else.

Do not wrap it in ```json code fences.

Do not add an introduction.

Do not add a conclusion.

Do not explain your reasoning outside the JSON.

Include the human-readable summary only inside the `batch_summary` field."

This allows the user to copy/save the response directly as:

001_vocabulary_batch_001_RESPONSE.json

==================================================
71. SINGLE RESPONSE FOLDER FOR ALL GPT RETURNS
==================================================

All GPT-returned JSON files go directly into:

enrichment/manual/responses/

Example:

001_vocabulary_batch_001_RESPONSE.json
002_vocabulary_batch_002_RESPONSE.json
003_verbs_batch_001_RESPONSE.json
004_expressions_batch_001_RESPONSE.json
...

No internal collection folders.

The scripts must infer the batch from:

- filename;
- `batch_id`;
- collection field;
- manifest.

Do not rely only on filename.

==================================================
72. BULK VALIDATE ALL RETURNED JSON FILES IN ONE COMMAND
==================================================

The validator must support folder mode.

Recommended:

python scripts/validate_enrichment_response.py \
  --folder enrichment/manual/responses/

It must:

1. scan all `.json` files in the response folder;
2. sort them by global batch sequence;
3. match each response to its batch manifest;
4. validate every file independently;
5. continue processing other files even if one fails;
6. never modify master;
7. produce per-batch validation results;
8. produce one combined validation summary.

Example terminal output:

Bulk validation complete.

Responses found: 10
Passed: 9
Review required: 1
Failed: 0

Per batch:
001_vocabulary_batch_001  PASS
002_vocabulary_batch_002  PASS
003_verbs_batch_001       REVIEW REQUIRED
...

Combined report:
enrichment/manual/reports/BULK_VALIDATION_REPORT.txt

==================================================
73. BULK PREVIEW ALL RETURNED JSON FILES IN ONE COMMAND
==================================================

Support:

python scripts/preview_enrichment.py \
  --folder enrichment/manual/responses/

or preferably from validated outputs:

python scripts/preview_enrichment.py \
  --folder enrichment/manual/validated/

This must generate:

A. one preview report for each batch;
B. one combined human-readable report covering all selected batches.

Example:

enrichment/manual/reports/
  001_vocabulary_batch_001_PREVIEW_REPORT.txt
  002_vocabulary_batch_002_PREVIEW_REPORT.txt
  003_verbs_batch_001_PREVIEW_REPORT.txt
  BULK_PREVIEW_REPORT.txt

`BULK_PREVIEW_REPORT.txt` should make checking 10, 20, or more returned batches
easy without opening raw JSON.

==================================================
74. ONE-COMMAND BULK APPLY FROM RESPONSE/APPROVED FOLDER
==================================================

The system must support applying MANY completed GPT batches in one command.

Recommended safe default:

python scripts/apply_enrichment.py \
  --folder enrichment/manual/approved/

If the workflow is configured so validated non-conflicting responses can be
treated as approved, optionally support:

python scripts/apply_enrichment.py \
  --folder enrichment/manual/responses/ \
  --validate-first \
  --skip-conflicts

However, the SAFEST recommended flow is:

responses
→ bulk validate
→ bulk preview
→ approved
→ bulk apply

For example, after the user has reviewed 10 returned batches and placed the
approved versions in:

enrichment/manual/approved/

run:

python scripts/apply_enrichment.py \
  --folder enrichment/manual/approved/

This one command must incorporate all approved JSON patches in deterministic
sequence.

==================================================
75. BULK APPLY MUST BE TRANSACTION-SAFE
==================================================

When applying a folder of batches:

1. load original master once;
2. calculate starting hash;
3. create one backup before the bulk operation;
4. sort batch files by global sequence;
5. revalidate each patch;
6. apply each batch IN MEMORY;
7. track every accepted operation;
8. track conflicts/no-ops/rejections;
9. after ALL selected batches are staged:
   - validate entire resulting master;
   - validate references;
   - validate duplicates;
   - validate structural integrity;
10. only if the final complete result passes:
   - atomically write the new master;
11. if a critical final validation fails:
   - do not overwrite master;
   - write a bulk failure report.

Optional configuration:

BULK_APPLY_MODE = "atomic"

Recommended default:
atomic.

Meaning:
all selected safe/approved batches are staged, then one final validated master
is committed.

==================================================
76. BULK APPLY FAILURE POLICY
==================================================

Two modes may be supported:

A. ATOMIC — DEFAULT

If a critical structural/schema failure occurs:
write NONE of the staged changes.

B. PER_BATCH

Apply each passing batch independently and commit after each.

This can be useful later, but DEFAULT should remain:

BULK_APPLY_MODE = "atomic"

because it gives the strongest protection.

Ordinary content conflicts that are explicitly configured to be skipped do
not necessarily count as fatal structural failures.

82. AUTOMATIC STATUS UPDATES
==================================================

Scripts should update the central manifest safely.

Example lifecycle:

generated
→ response_received
→ validated
→ approved
→ applied

If a returned JSON exists in responses but manifest still says generated,

response_received

Never mark a batch applied unless the actual master update succeeds.

==================================================
83. WHOLE-DATASET QUEUE SHOULD SUPPORT MULTIPLE ENRICHMENT PASSES
==================================================

The complete dataset may be enriched in several passes.

Example:

PASS 1:
basic lexical/usage enrichment

PASS 2:
missing structural information

PASS 3:
examples and cross-links

PASS 4:
high-risk grammar/conjugation review

Support a configurable:

ENRICHMENT_PASS_NAME = "pass_1_general"

The batch manifest should record the pass.

If desired, filenames can remain simple while the manifest records the pass.

Alternatively:

001_vocabulary_pass1_batch_001.txt

But the simpler default naming is preferable:

001_vocabulary_batch_001.txt

==================================================
84. RESPONSE FILE MATCHING
==================================================

A returned JSON must include:

{
  "batch_id": "001_vocabulary_batch_001",
  "collection": "vocabulary",
  ...
}

The validator must match this against the manifest.

If the user accidentally names the file incorrectly but the internal
`batch_id` is correct, the validator may warn and still identify the batch.

If internal batch_id is wrong or missing:
reject/review.

==================================================
85. FINAL USER WORKFLOW
==================================================

INITIAL SETUP:

1. Configure default batch sizes.

2. Generate the entire queue:

   python scripts/make_enrichment_batch.py --all

3. Open:

   enrichment/manual/batches/

4. Slowly take batch TXT files one by one.

FOR EACH GPT SESSION:

5. Drop/upload one TXT file into high-quality GPT.

6. GPT returns JSON ONLY.

7. Save the returned JSON into:

   enrichment/manual/responses/

   using the corresponding response name.

Example:

Batch:
001_vocabulary_batch_001.txt

Returned file:
001_vocabulary_batch_001_RESPONSE.json

AFTER DOING MULTIPLE BATCHES:

8. Suppose the user completes 10 batches.

9. Put all 10 JSON responses in:

   enrichment/manual/responses/

10. Run one command:

   python scripts/process_enrichment_folder.py \
     enrichment/manual/responses/

11. Read:

   enrichment/manual/reports/BULK_PREVIEW_REPORT.txt

12. Review additions/conflicts without opening raw JSON.

13. Place approved JSON patches in:

   enrichment/manual/approved/

14. Apply all approved batches at once:

   python scripts/apply_enrichment.py \
     --folder enrichment/manual/approved/

15. Read:

   enrichment/manual/reports/BULK_APPLIED_REPORT.txt

This is the intended everyday workflow.

==================================================
86. FINAL SIMPLICITY REQUIREMENT
==================================================

The system should feel simple to use even though it is strict internally.

The normal user experience should be:

ONE COMMAND:
generate all batch TXT files

↓ slowly enrich them in GPT

ONE FOLDER:
store returned JSON files

ONE COMMAND:
validate + preview all returned JSONs

ONE TXT:
review what will be added

ONE COMMAND:
apply all approved JSONs

ONE TXT:
review what was actually added

The scripts handle all structural complexity.

The user should never need to manually edit MASTER_DATA.json.
